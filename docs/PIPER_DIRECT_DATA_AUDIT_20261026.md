## 范围与结论

核查原包：`data/2026-10-26/banana_into_box/scene-a06/banana-direct-a06-001/`。
用户已确认香蕉实际放进盒子；一个人操作时存在停顿。本次保留为现场确认成功的人工演示，
不是操作失败。程序仅离线读取 rosbag，没有访问 CAN 或发布控制消息。

**结论：不能把所有动作时间间隔都称为采集丢帧。** 最长动作间隔也存在于已记录的原始目标帧中，
不是本次七维解码器漏掉了已有记录。原始话题仍来自电脑接收链路；没有第二路独立总线记录，
因此不能凭本包区分“发送端没有发送”与“进入原始话题前就未收到”，也不证明固件停发规则。
图像时间间隔则是另一项问题，不能由人工停顿解释全部图像间隔。

## 1. 动作话题与原始帧对照

以首个 `start` 到首个 `success` 为任务窗口，时长 `47.330241s`：

- 动作话题在窗口内记录 `5156` 条。将保存的原始命令按接收时间离线送入现有 `FrameSet`

  与动作话题的源时间戳集合完全一致，没有“可从原始记录重建但未录入动作话题”的条目。
  重放使用保存的主机接收时间，而不是原进程未保存的单调时钟；这里只作为本包交叉证据。
- 任务窗口内四类目标帧都没有超过 100ms 的接收时间差。整包夹爪目标的模式均为
  `status=0x01 / set_zero=0x00`，未发现本包动作间隔由夹爪失能/设零过滤导致的证据。

## 5. SDK 与运动模式核对

用户在终端 02 打印本机 `C_PiperInterface_V2.JointCtrl`、`MotionCtrl_2` 源码；未创建
机械臂连接或调用控制方法。源码确认关节目标单位为 `0.001°`、模式指令 ID 为 `0x151`，
但没有描述停止发送后的保持期限、固件通信超时或目标失效规则。`residence_time` 是离线轨迹点
停留时间，不是 CAN 通信超时或最后目标保持时间。

随后从本次保存的原包统计 `0x151`：476 条均为 `01 01 64 AD 00 00 00 00`。按本机
SDK 字段解释，对应 CAN 控制、MOVE J、速度百分比 100、`is_mit_mode=0xAD`（MIT 标志）。
这里是观察已有帧，未发送或修改任何模式。该标志不等于已经证实底层全部固件行为，
也不意味着已观察到逐电机 `0x15A~0x15F` 控制帧。

官方 `piper_sdk/demo/V2/piper_ctrl_joint.py` 示例使用 `is_mit_mode=0x00`，并在约 5ms
循环中重复调用模式、关节和夹爪命令。示例只说明该示例的发送方式，不证明当前直连配置的
通信超时，更不能据此把 `0xAD` 配置套成普通位置速度模式。
参考：[官方关节示例](https://github.com/agilexrobotics/piper_sdk/blob/master/piper_sdk/demo/V2/piper_ctrl_joint.py)。

本次核对未找到可据以确认当前固件“无限保持最后目标”的依据。目标保持语义继续标记为未知，
不因此要求空载试验或立即重录，不放宽新鲜度阈值。后续可继续离线格式适配和相机链路诊断，
